Release date: 2026-10-02 (Pacific/Auckland). RC, not GA.

## Decision and log-order findings

PostgreSQL sequence values are allocated before commit and are not transactional.
The existing `position`/single-event-ID resume cursor can observe position 2 before
position 1 commits, then omit 1 forever. It remains compatible for quiescent
export/import/rebuild; it is not a concurrent commit-order feed. No global lock was
introduced to pretend otherwise. Existing bigint position cursors now retain their
string precision rather than rounding through JavaScript Number.

The implemented alternative is a checkpoint per stream. Pages advance only streams
whose rows were returned, and same-stream locks prevent a later sequence committing
before an earlier one. This prevents the tested late-commit omission, including
new streams, while allowing unrelated streams to commit independently. It is not a
global cross-page causal order, total commit order or atomic-batch projection feed;
use logical decoding/CDC when those are required. The checkpoint's scope is one
physical table and its lifecycle; it must not be reused after reset or restore.

Decision validation covers the finite listed write and read-only streams. A global
adapter head ID is not supported: unlisted/new streams are outside that baseline.
For whole consumer-scope decisions, every writer must append a consumer-owned scope
revision event in its batch, and commands check that revision's expected version.
A test demonstrates rejecting a stale decision after an otherwise unlisted stream
changes. Different consumer scopes remain independent. Projection state and its
baseline must be read consistently; sampling a fresh baseline after an old
projection does not prove that decision current.

Primary references: [node-postgres transaction connection requirements](https://node-postgres.com/features/transactions),
[PostgreSQL READ COMMITTED and nontransactional sequences](https://www.postgresql.org/docs/15/transaction-iso.html),
[transaction advisory locks and lock order](https://www.postgresql.org/docs/15/explicit-locking.html).

## Compatibility and adoption

`append` and valid `appendToStream` calls retain their signatures and return values.
Multi-stream `append` now preserves caller log order instead of grouping inserts;
it remains one atomic transaction and still generates IDs. `appendToStream` rejects
illegal expected versions. Primary-ID duplicates now have a typed error. New
capabilities are optional; core and SQLite do not acquire mandatory PG methods or
pg dependencies. Event bodies and existing stream sequences are not rewritten.

The already-pending V6 simplification is also part of this RC: `StoredEvent`/`Event`
aliases are removed in favor of `PersistedEvent`; `PhaseContext` is removed in favor
of `AggregateContext`; mandatory `capabilities` properties are removed in favor of
method detection. Consumers relying on these removed names/properties must update
and typecheck. This is a prerelease compatibility change, not a GA stability promise.

Six public packages (`types`, `core`, `aggregate`, `adapter-pg`,
`adapter-expo-sqlite`, `revert`) and the private reference example are versioned
**6.0.0-rc.6**, with internal dependency ranges updated together. Pin matching exact
RC versions in Ginko during evaluation rather than mixing contracts across RCs:

```sh
yarn add @schemeless/event-store-types@6.0.0-rc.6 \
  @schemeless/event-store-core@6.0.0-rc.6 \
  @schemeless/event-store-aggregate@6.0.0-rc.6 \
  @schemeless/event-store-adapter-pg@6.0.0-rc.6
```

Stop writers for initialization/schema setup; upgrade **every writer** to RC.6
before enabling the cooperative stream-lock contract. Old writers/direct event-table
SQL do not participate. Keep transactions short, perform external/LLM work first,
and put deduplication, authorization locks, events and receipts in the callback.
Retry the complete transaction with fresh decisions on version conflicts, deadlocks,
serialization errors or timeouts. For ambiguous COMMIT network failures, recover
through the same durable command ID; do not blindly submit a new command ID.

## Explicitly unverified boundaries

- Expo SQLite regressions use the existing mocked Expo database; a real mobile Expo
  SQLite device/runtime was not exercised. Its source is compiled with the new types.
- PostgreSQL versions other than 15, replicas, RLS/multitenant policy designs, logical
  decoding integration and consumer-specific authorization models are not validated.
- No injected network loss during COMMIT, process-kill recovery, pool exhaustion,
  production-scale benchmarks or exhaustive concurrency fuzzing were run.
- Cross-table consumer SQL can still deadlock; sorted stream locks prevent the tested
  stream-order deadlock, not every possible application lock cycle.
- Vector size is linear in stream count. Unbounded concurrent traffic can starve
  pages; CDC is the alternative for an unbounded globally ordered feed.
- Legacy NULL sequences are refused by the incremental API; no migration rewrites
  them. Out-of-band event mutation, reset or restore invalidates checkpoints.
- Permissions, tenant isolation and receipt retention/cleanup remain consumer-owned.
